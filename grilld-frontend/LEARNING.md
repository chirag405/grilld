# Grilld Frontend — Learning Log

Phase 9 of the overall build (see the repo root's `LEARNING.md` for Phases 1-8, the Spring Boot backend, and `grilld-ai-service/LEARNING.md` for the Python AI service). Per the project's original kickoff plan, the entire backend was built and fully tested end to end before any frontend code existed - this file starts from a working, deployed-locally API, not a stub.

## Task 1: scaffold, design system, auth, and the interview loop

### Next.js 16, not 15 - and why that mattered before writing a line of UI

`product-and-architecture.md` §8 specs "Next.js 15" - written before Next.js 16 shipped (Oct 2025, now LTS). `create-next-app@latest` scaffolds 16 by default, and the version gap isn't cosmetic: Cache Components (opt-in via `cacheComponents: true` in `next.config.ts`) replaces the old implicit caching model, `params`/`searchParams` are now Promises everywhere, `middleware.ts` is renamed `proxy.ts`, and new globally-available typed helpers (`PageProps<'/route'>`, `LayoutProps<'/route'>`, `RouteContext<'/route'>`) generate from the actual route tree via `next dev`/`next build`/`next typegen`. Per the Research-First Rule, all of this was read directly from `node_modules/next/dist/docs/` - the exact docs matching the installed version, bundled with the package itself precisely because generic training data goes stale here - rather than assumed from Next.js 15 familiarity. `AGENTS.md` (generated by `create-next-app`, re-added by `next dev` if removed) says as much explicitly: "This is NOT the Next.js you know."

**Cache Components was deliberately left off** (the scaffold's default - `next.config.ts` doesn't set it). Its entire value proposition is static shells, ISR, and prerendering for content that's the same across visitors. Nothing in Grilld is: every real screen is behind auth and shows one user's own session, brief, or run state. Turning it on would mean annotating routes that gain nothing from it just to satisfy the framework's own validation. Worth revisiting only if a genuinely public, cacheable page (marketing, docs) gets built later.

### The design: a blueprint, not a chat app

Every AI-app default right now clusters around three looks (cream+serif+terracotta, near-black+neon, broadsheet-serif) - all considered and rejected as defaults, not choices tied to this brief. The chosen direction instead comes from what Grilld's own output literally is: an architecture, an infra plan, a phased build order - a blueprint, the word the product already uses for itself. Token system:

- **Color**: `--color-paper` (#F7F5F0, tracing-paper warm white) + `--color-ink` (#14213D, deep blueprint navy for text) + `--color-blueprint`/`--color-blueprint-line` (cyanotype blues, #0B3D91/#7FA8D9, for linework and the brand accent) + `--color-rust` (#E8590C, the one warm accent - "the heat of being grilled," spent sparingly on CTAs, never paired with black to avoid drifting into the neon-on-black cliché).
- **Type**: Space Grotesk (display, restrained - headlines only) + Inter (body) + IBM Plex Mono (utility - slot keys, credit counts, the title-block labels, run status). Loaded via `next/font/google` with distinct CSS variable names (`--font-space-grotesk` etc.) from the Tailwind `@theme` tokens (`--font-display` etc.) that reference them with a fallback stack - `next/font` and Tailwind's `@theme` both trying to own the literal same custom property name is a real collision, not a hypothetical one.
- **Signature element**: the title block. Real engineering/architectural drawings carry a small compartmented block (project, drawn-by, scale, revision) in a corner. Recurs as `TitleBlockPanel` - the live brief panel's frame - so the one memorable visual idea is also the one doing real information work, not decoration bolted onto an otherwise generic screen. `.blueprint-sheet` (a faint 24px cyanotype grid) is the recurring background texture tying every screen to the same drafting-table surface.
- Verified in a real headless-Chromium screenshot before treating it as done (see `browser-automation` skill usage below), not just read as JSX.

### Auth: httpOnly cookie + a BFF proxy, not a client-readable token

`OAuth2LoginSuccessHandler` (Spring, Phase 9's backend-side changes - see the repo root `LEARNING.md`) redirects to `/auth/callback?token=...` after a real Google login. That route (`src/app/auth/callback/route.ts`) is a Next.js Route Handler - the pattern is taken directly from `node_modules/next/dist/docs/.../backend-for-frontend.md`'s own "Webhooks and callback URLs" example, adapted rather than invented - which moves the token into an httpOnly, `sameSite: lax` cookie and redirects to `/interview`, so the JWT never sits in browser history or is readable by page JS.

That last property has a real consequence: Client Components can't attach an `Authorization` header themselves, because they can't read the cookie. Two different fetch paths follow from this, matching Next's own documented boundary ("fetch data in Server Components directly from its source, not via Route Handlers"):

- **Server Components** (`src/lib/api-server.ts`) call `grilld-backend` directly, reading the cookie server-side via `next/headers`'s `cookies()`.
- **Client Components** (`src/lib/api-client.ts`) always go through `/api/proxy/[...path]/route.ts` - a single catch-all Route Handler that reads the cookie, attaches the Bearer token, and forwards to Spring. It streams the upstream response body straight through unmodified (`new Response(upstream.body, {...})`), which is what makes the same handler work for both plain JSON and the Run Report's `text/event-stream` SSE connection without any special-casing - EventSource can't set custom headers either, so it has the identical problem plain `fetch()` does from a Client Component, and the same proxy fixes both.

Verified this whole chain works, not just compiles: with a real dev server running end to end (Spring Boot on 8080 with the `StubAiServiceClient` active, Next on 3001) and a deliberately *invalid* token cookie set via Playwright, submitting the idea form produced a real `401` from Spring's JWT filter, correctly forwarded through the proxy, correctly caught and rendered as a clean error message by the interview page - proving request forwarding, header injection, and error propagation all work, using the one failure mode (bad auth) that's actually reachable without real Google credentials.

### What wasn't browser-verified, and why

A real Google OAuth login round trip needs `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, which aren't configured in this environment - the same category of manual-only check `docs/phases/phase-1/TESTING.md` already carves out for the backend's own OAuth login. The interview page's happy path (real question → real answer → real brief update) is therefore verified by construction (the response shapes in `src/lib/types.ts` are typed against the exact same Java records `SessionFlowIntegrationTest` asserts on, field for field) and by the landing-page/error-path browser checks above, not by watching a real interview happen in a browser. Flagged here rather than claimed as done - `docs/phases/phase-9/TESTING.md`'s manual checklist is where a real Google login and the full interview loop need to be exercised by hand once real OAuth credentials exist.

### Honest gaps, not faked

- **Chip input has no real option values.** `InterrogatorTurnResult.NextQuestion.inputMode` can be `"chips"` per the spec, but nothing in the Python/stub AI service has ever populated concrete chip choices - there's no field for them. `AnswerForm` falls back to free text for `chips` and `voice_primary` rather than inventing plausible-looking labels a real Interrogator never asked for.
- **No speech-to-text exists anywhere in this stack.** `voice_primary` is a real, spec'd input mode (`product-and-architecture.md` §1 is an entire section on voice as the primary input); the frontend doesn't fake a working microphone button for a capability that doesn't exist yet.
- **Progress during generation is polled, not streamed live.** `GenerationPanel` polls `GET .../report` every 2s rather than opening `RunReportController`'s SSE endpoint - a real, working view of a run completing, but not yet the diff-highlighting live canvas `decisions-and-technical-architecture.md` §10.3 describes. The proxy route is already built to support SSE (see above); wiring `EventSource` to it is scoped, not-yet-done follow-up work, not a redesign.
- **Doc browser, Mermaid preview, and the billing/checkout UI don't exist yet.** `GenerationPanel` only offers the finished zip download. Scoped as later Phase 9 tasks.
