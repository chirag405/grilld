# Grilld Frontend — Learning Log

Phase 9 of the overall build (see the repo root's `LEARNING.md` for Phases 1-8, the Spring Boot backend, and `grilld-ai-service/LEARNING.md` for the Python AI service). Per the project's original kickoff plan, the entire backend was built and fully tested end to end before any frontend code existed - this file starts from a working, deployed-locally API, not a stub.

## Task 1: scaffold, design system, auth, and the interview loop

### Next.js 16, not 15 - and why that mattered before writing a line of UI

`product-and-architecture.md` §8 specs "Next.js 15" - written before Next.js 16 shipped (Oct 2025, now LTS). `create-next-app@latest` scaffolds 16 by default, and the version gap isn't cosmetic: Cache Components (opt-in via `cacheComponents: true` in `next.config.ts`) replaces the old implicit caching model, `params`/`searchParams` are now Promises everywhere, `middleware.ts` is renamed `proxy.ts`, and new globally-available typed helpers (`PageProps<'/route'>`, `LayoutProps<'/route'>`, `RouteContext<'/route'>`) generate from the actual route tree via `next dev`/`next build`/`next typegen`. Per the Research-First Rule, all of this was read directly from `node_modules/next/dist/docs/` - the exact docs matching the installed version, bundled with the package itself precisely because generic training data goes stale here - rather than assumed from Next.js 15 familiarity. `AGENTS.md` (generated by `create-next-app`, re-added by `next dev` if removed) says as much explicitly: "This is NOT the Next.js you know."

**Cache Components was deliberately left off** (the scaffold's default - `next.config.ts` doesn't set it). Its entire value proposition is static shells, ISR, and prerendering for content that's the same across visitors. Nothing in Grilld is: every real screen is behind auth and shows one user's own session, brief, or run state. Turning it on would mean annotating routes that gain nothing from it just to satisfy the framework's own validation. Worth revisiting only if a genuinely public, cacheable page (marketing, docs) gets built later.

### The design: a blueprint, not a chat app

Every AI-app default right now clusters around three looks (cream+serif+terracotta, near-black+neon, broadsheet-serif) - all considered and rejected as defaults, not choices tied to this brief. The chosen direction instead comes from what Grilld's own output literally is: an architecture, an infra plan, a phased build order - a blueprint, the word the product already uses for itself. Token system:

- **Color**: `--color-paper` (#F7F5F0, tracing-paper warm white) + `--color-ink` (#14213D, deep blueprint navy for text) + `--color-blueprint`/`--color-blueprint-line` (cyanotype blues, #0B3D91/#7FA8D9, for linework and the brand accent) + `--color-rust` (#E8590C, the one warm accent - "the heat of being grilled," spent sparingly on CTAs, never paired with black to avoid drifting into the neon-on-black cliché).
- **Type**: Space Grotesk (display, restrained - headlines only) + Inter (body) + IBM Plex Mono (utility - slot keys, credit counts, the title-block labels, run status). Loaded via `next/font/google` with distinct CSS variable names (`--font-space-grotesk` etc.) from the Tailwind `@theme` tokens (`--font-display` etc.) that reference them with a fallback stack - `next/font` and Tailwind's `@theme` both trying to own the literal same custom property name is a real collision, not a hypothetical one.
- **Signature element**: the title block. Real engineering/architectural drawings carry a small compartmented block (project, drawn-by, scale, revision) in a corner. Recurs as `TitleBlockPanel` - the live brief panel's frame - so the one memorable visual idea is also the one doing real information work, not decoration bolted onto an otherwise generic screen. `.blueprint-sheet` (a faint 24px cyanotype grid) is the recurring background texture tying every screen to the same drafting-table surface.
- Verified in a real headless-Chromium screenshot before treating it as done (see `browser-automation` skill usage below), not just read as JSX.

### Auth: httpOnly cookie + a BFF proxy, not a client-readable token

`OAuth2LoginSuccessHandler` (Spring, Phase 9's backend-side changes - see the repo root `LEARNING.md`) redirects to `/auth/callback?token=...` after a real Google login. That route (`src/app/auth/callback/route.ts`) is a Next.js Route Handler - the pattern is taken directly from `node_modules/next/dist/docs/.../backend-for-frontend.md`'s own "Webhooks and callback URLs" example, adapted rather than invented - which moves the token into an httpOnly, `sameSite: lax` cookie and redirects to `/interview`, so the JWT never sits in browser history or is readable by page JS.

That last property has a real consequence: Client Components can't attach an `Authorization` header themselves, because they can't read the cookie. Two different fetch paths follow from this, matching Next's own documented boundary ("fetch data in Server Components directly from its source, not via Route Handlers"):

- **Server Components** (`src/lib/api-server.ts`) call `grilld-backend` directly, reading the cookie server-side via `next/headers`'s `cookies()`.
- **Client Components** (`src/lib/api-client.ts`) always go through `/api/proxy/[...path]/route.ts` - a single catch-all Route Handler that reads the cookie, attaches the Bearer token, and forwards to Spring. It streams the upstream response body straight through unmodified (`new Response(upstream.body, {...})`), which is what makes the same handler work for both plain JSON and the Run Report's `text/event-stream` SSE connection without any special-casing - EventSource can't set custom headers either, so it has the identical problem plain `fetch()` does from a Client Component, and the same proxy fixes both.

Verified this whole chain works, not just compiles: with a real dev server running end to end (Spring Boot on 8080 with the `StubAiServiceClient` active, Next on 3001) and a deliberately *invalid* token cookie set via Playwright, submitting the idea form produced a real `401` from Spring's JWT filter, correctly forwarded through the proxy, correctly caught and rendered as a clean error message by the interview page - proving request forwarding, header injection, and error propagation all work, using the one failure mode (bad auth) that's actually reachable without real Google credentials.

### What wasn't browser-verified, and why

A real Google OAuth login round trip needs `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, which aren't configured in this environment - the same category of manual-only check `docs/phases/phase-1/TESTING.md` already carves out for the backend's own OAuth login. The interview page's happy path (real question → real answer → real brief update) is therefore verified by construction (the response shapes in `src/lib/types.ts` are typed against the exact same Java records `SessionFlowIntegrationTest` asserts on, field for field) and by the landing-page/error-path browser checks above, not by watching a real interview happen in a browser. Flagged here rather than claimed as done - `docs/phases/phase-9/TESTING.md`'s manual checklist is where a real Google login and the full interview loop need to be exercised by hand once real OAuth credentials exist.

### Honest gaps, not faked (as of Phase 9 - see below for what later work closed)

- **Chip input has no real option values.** `InterrogatorTurnResult.NextQuestion.inputMode` can be `"chips"` per the spec, but nothing in the Python/stub AI service has ever populated concrete chip choices - there's no field for them. `AnswerForm` falls back to free text for `chips` and `voice_primary` rather than inventing plausible-looking labels a real Interrogator never asked for.
- **No speech-to-text exists anywhere in this stack.** `voice_primary` is a real, spec'd input mode (`product-and-architecture.md` §1 is an entire section on voice as the primary input); the frontend doesn't fake a working microphone button for a capability that doesn't exist yet. *(Recording/upload plumbing built in Phase 12, below - the provider itself still isn't chosen.)*
- **Progress during generation is polled, not streamed live.** `GenerationPanel` polls `GET .../report` every 2s rather than opening `RunReportController`'s SSE endpoint. *(Fixed in Phase 11 - see below.)*
- **Doc browser, Mermaid preview, and the billing/checkout UI don't exist yet.** `GenerationPanel` only offers the finished zip download. *(Billing UI shipped in the post-Phase-9 polish round; Mermaid rendering and a single-document preview shipped in Phase 12 - both below. A full multi-file doc browser still doesn't exist.)*

## Later work: design overhaul, session history, billing UI, a logo (no dedicated phase folder)

A large batch of live-feedback-driven UI work landed between Phase 9 and Phase 12 without going through the phased-delivery checklist at the time - see the repo root `LEARNING.md`'s matching section for the full backend-side story (profile data, credits, session history endpoints). The frontend-visible pieces:

- **A full visual redesign** away from the original "blueprint/cyanotype" direction toward a warmer, more minimal system (`--color-paper`/`--color-ink`/`--color-accent`, Space Grotesk + Inter + IBM Plex Mono) - built entirely from components in the four curated kits (`frontend-component-kits` skill: prompt-kit, Motion Primitives, Aceternity UI, Watermelon UI), never hand-rolled from scratch.
- **A real logo** (`components/Logo.tsx`, a flame mark) as both the favicon (`app/icon.svg`) and the site wordmark.
- **A landing page agent-pipeline diagram** (`components/AgentPipelineDiagram.tsx`) using `@xyflow/react` (React Flow) - chosen because the content is a fixed shape (idea → interrogation → orchestrator → ten named specialists → output), so a static, hand-positioned set of nodes/edges with every interaction prop (`nodesDraggable`, `panOnDrag`, `zoomOnScroll`, etc.) deliberately turned off is simpler and more correct than pulling in a real auto-layout engine (dagre/elkjs) for content that never actually needs re-layout.
- **A real billing/checkout UI** (`app/billing/page.tsx`) using an adapted Watermelon `pricing-1` component, and a persistent, non-dismissable "you're out of credits" dialog in `GenerationPanel` (rather than disabling the generate button outright) - because the actual product decision was "let the user keep typing/answering for free; only gate the credit-spending generate step," which a disabled button can't express on its own.
- **Session history and resume** - `app/interview/page.tsx` grew a landing-screen list of past sessions (fetched via the new `GET /sessions` endpoint) and a `resumeSession()` function that rebuilds the chat transcript from `GET /sessions/{id}/turns`. Left genuinely incomplete until Phase 12 (below): resuming never checked whether the session already had a *finished blueprint*, so reopening a completed session showed an empty generation panel.

**A recurring vendored-component bug worth remembering**: Watermelon UI's shadcn-registry components sometimes use `render={<motion.div .../>}` on a Radix primitive, which the installed `radix-ui` version doesn't support (`Property 'render' does not exist`) - hit and fixed the same way in `dropdown-menu.tsx` and again in `dialog.tsx`: convert to `asChild` plus a wrapped child. Check for this specific pattern first if a freshly-installed Watermelon component fails to typecheck.

## Phase 12: voice recording, rendered diagrams, and a document preview

From a fresh full-project audit rather than a bug report - see `docs/phases/phase-12/README.md` for the complete picture (this covers the frontend-specific "why," matching this file's own depth).

**`VoiceRecorder.tsx` records real audio today; only the transcription call is stubbed.** Uses the browser's native `MediaRecorder` API directly (no library) - `navigator.mediaDevices.getUserMedia({audio: true})` for the mic permission prompt, then `MediaRecorder` to capture chunks into a `Blob`, uploaded as `multipart/form-data` to the new `POST /api/v1/voice/transcribe`. The transcribed text lands in the textarea for the user to review/edit, never auto-submitted - matches this project's existing rule that an AI-touched value is always a suggestion the human confirms, not an autonomous action.

**A real bug this surfaced: the proxy route silently corrupted binary bodies.** `src/app/api/proxy/[...path]/route.ts` forwarded every request body through `await request.text()` - fine for JSON, actively wrong for a multipart audio upload, since `.text()` runs a UTF-8 decode over what's really raw binary bytes, corrupting them before Spring ever sees them. Nothing before Phase 12 ever sent a binary body through this route, so the bug was latent, not previously visible. Fixed by switching to `request.arrayBuffer()`, which passes both JSON and binary bodies through unchanged - one line, but worth understanding *why* `.text()` was wrong rather than just swapping it blindly: it's the "decode as text, re-encode losing information" trap, the same class of bug as opening a binary file in a text editor and saving it back.

**Why `VoiceRecorder` doesn't go through `apiClient()`.** `src/lib/api-client.ts`'s `apiClient()` helper always sets `Content-Type: application/json` whenever a request body is present - correct for every other call in this app, wrong here, since a `FormData` body needs the browser to set its own `Content-Type` (with a random multipart boundary the server needs to parse the body correctly) - manually setting it strips that boundary and breaks the upload. Used a plain `fetch()` instead, mirroring the existing pattern for the zip download link (`<a href="/api/proxy/.../download">`), which also deliberately bypasses `apiClient()` for the same class of reason (non-JSON payload).

**`MermaidDiagram.tsx` renders Mermaid source into a real inline SVG**, client-side, via the `mermaid` npm package - `mermaid.render()` is async (it returns a Promise, not a value), so the component starts in a loading-skeleton state and swaps in the real SVG once rendering resolves; a chart that fails to parse falls back to showing the raw text rather than a blank gap. `securityLevel: "strict"` matters here specifically because the diagram source comes from AI-generated content, not a hardcoded string - it sanitizes the output SVG so injecting it via `dangerouslySetInnerHTML` is actually safe. Wired into `components/ui/markdown.tsx`'s existing code-block renderer (checking for `language-mermaid`), which means every place `<Markdown>` already renders - chat messages, the Run Report, the new document preview below - picked up real diagram rendering for free, with no changes needed at any of those call sites.

**A lint rule worth understanding, not just satisfying: `react-hooks/set-state-in-effect`.** Both new components initially called `setState` synchronously at the top of a `useEffect` body (resetting `svg`/`failed` before starting an async Mermaid render; computing microphone-support via `useEffect` + `setState` instead of directly). The rule's actual point: an effect should either *synchronize with an external system* or *subscribe and update state from a callback when that external thing changes* - not use an effect as an alternate code path for something you could just compute during render. Fixed both properly rather than reaching for `eslint-disable`: the Mermaid component no longer clears state before its async call, it just lets stale content stay on screen until the new render resolves (arguably better UX - no flicker); `VoiceRecorder`'s browser-capability check (`navigator.mediaDevices`, `MediaRecorder`) is now a plain `const` computed directly in the function body, since it never changes during the component's life and this component never actually renders during the server's initial pass anyway (voice_primary only appears after an async session fetch resolves client-side) - so there's no hydration-mismatch risk to guard against by deferring it into an effect.

**`GET /sessions/{id}/runs` plus a restore-on-mount effect in `GenerationPanel` closes the incomplete session-resume gap** from the polish round above. On mount, the panel now fetches the session's persisted scale tier (`GET /sessions/{id}`) and its most recent run (`GET /sessions/{id}/runs`) in parallel, before the user does anything - the existing report-polling/SSE effect (unchanged) then does the right thing automatically whether the restored run is still `IN_PROGRESS`, already `COMPLETED`, or `FAILED`. The `FAILED` case exposed a real, separate gap while fixing this one: there was previously no way to retry a failed run from the UI at all (the generate button only ever showed when no run existed yet) - added a "Try again" path gated on `report?.status === "FAILED"`.

**A small, deliberately-scoped document preview, not a doc browser.** `GET /sessions/{id}/runs/{runId}/documents?path=...` (new backend endpoint) plus a click-to-open `Dialog` in `GenerationPanel` lets a completed document's real content be read - rendered through the same `Markdown`/`MermaidDiagram` pipeline as everything else - before committing to a full zip download. This is the smallest thing that makes the new Mermaid renderer reachable anywhere in the actual running app (without it, nothing currently displayed by the app ever contained a mermaid-fenced block); a full multi-file browser with a file tree is explicitly not what this is.

**Fish Audio chosen as the real transcription provider (backend-only change).** `VoiceRecorder.tsx` needed zero code changes once the user picked Fish Audio - the whole point of the `TranscriptionService` seam on the backend (see the repo root `LEARNING.md` for the real integration story: fetching Fish Audio's actual OpenAPI contract live rather than assuming it, the multipart/Bearer-auth request shape, `MockRestServiceServer`-based testing) is that the frontend never knows or cares which provider is behind `POST /api/v1/voice/transcribe`, only whether the call succeeded or came back with an honest error. Only the two doc comments in `AnswerForm.tsx`/`VoiceRecorder.tsx` needed updating, since they'd said "no provider configured" and that stopped being true.
