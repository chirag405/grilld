# Phase 4 — Testing (the gate for Phase 5)

## Automated

- [x] `uv run pytest` (Python, unit) — `detect_vagueness` (6 cases) and `_compute_verdict` (all-PASS accepts, single BORDERLINE blocks, any FAIL blocks) - no API key or live services needed.
- [x] `uv run pytest tests/integration_tests/test_interrogator.py` — **real** Claude calls: opening turn restates the specific idea and uses `ASSUMPTION_SURFACING`; a vague answer ("scale well and be fast") forces the next question into `CONCRETIZATION`.
- [x] `uv run pytest tests/integration_tests/test_rubric.py` — **real** Claude calls: a brief with almost everything `OPEN` is rejected (`probe_further`, non-empty `open_gaps`, all 6 dimensions scored); a brief with explicit numbers, named risks, a genuine scope-exclusion list, and validated technical constraints is accepted (`accept`). This test failed twice during development on realistic-but-incomplete fixtures before a fixture was found the judge genuinely accepted - see `LEARNING.md`'s Phase 4 section for what each failure revealed.
- [x] `./mvnw test` (Java, full suite) — 7 tests, 0 failures: existing Phase 1-3 tests unchanged, plus `RubricGateTest` (2 new cases: accepted rubric actually concludes and persists a `RubricEvaluation` row; rejected rubric asks one more targeted question instead of concluding, and does **not** mark the session concluded). `ContradictionDetectionTest` (Phase 4's earlier addition) still passes unchanged.

## Manual — verified this session

- [x] **Full live round trip through the real Interrogator**: fresh Google OAuth login → `POST /api/v1/sessions` with a real idea ("a tool for freelancers to track which invoices are unpaid") → got back a real, idea-specific restatement using `ASSUMPTION_SURFACING`, not a template. `POST .../answer` with a real answer → real extraction (`problem_statement` filled with confidence 0.95, verified directly in Postgres) → a real, on-topic follow-up question. This is the first time `HttpAiServiceClient`'s real structured-output parsing (not the Phase 3 placeholder) was exercised against a live Claude response, not just a mocked test.
- [x] **A real bug found and fixed via live testing, not caught by the mocked suite**: driving a longer multi-turn interview by hand hit a raw `NullPointerException` (500) when the Interrogator returned `next_question: null` with `ready_to_conclude: false`. Fixed in `SessionService` (see phase README's "Known limitations"); the full Java test suite (including the pre-existing tests) still passes after the fix.
- [x] Restarting Spring Boot mid-session correctly regenerates the ephemeral JWT signing key (expected, documented since Phase 1) - re-authenticating via Google and retrying with a fresh token worked as expected both times this phase.

## Deferred, not proven this session

- [ ] **A full live interview run all the way to a real rubric-gated conclusion.** Live testing got several turns deep and proved the extraction/persistence/next-question loop for real, but the interview didn't reach `ready_to_conclude` before the session moved on to the next piece of work (browser automation became unreliable for re-authenticating, see below). The gate's actual behavior at that decision point - accept vs. reject vs. retry-with-targeted-question - is proven by `RubricGateTest` against scripted `AiServiceClient` responses (both branches, including the retry-then-still-null-question escape hatch), which is a faithful test of `SessionService`'s own logic regardless of what the real Interrogator/Rubric Agent ever return. What's *not* independently reproduced live is the real Interrogator actually reaching `ready_to_conclude=true` on its own and the real Rubric Agent independently agreeing or disagreeing with it in the same run.
- [ ] Browser-driven re-authentication became unreliable partway through this phase (Chrome extension screenshot tool started erroring; clicks on Google's account-chooser stopped visibly registering even via element-reference targeting, not just coordinates). Not investigated further per the "avoid rabbit holes" guidance - flagging here rather than silently working around it. A manual browser login (or a longer-lived non-ephemeral JWT signing key, tracked as a pre-existing Phase 1 limitation) would remove this friction for future live-testing sessions.

## Sign-off

Phase 4's stated gate - "a full mock interview runs start to finish with real dynamically-generated questions and periodic rubric evaluation" - is met at the code/automated-test level for every individual piece (real question generation, real extraction, real contradiction detection, real rubric scoring, real gate control-flow including both accept and reject branches), and the Interrogator-side live round trip was independently confirmed against real Claude output. The one gap is an end-to-end live run reaching the gate itself, blocked on browser tooling rather than any known code issue - tracked above rather than silently assumed solved, consistent with how Phase 3's checkpoint-persistence gap was handled.
