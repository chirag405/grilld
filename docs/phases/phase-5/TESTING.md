## Manual / real-model findings this session

- [x] **Groq works for structured-output-only graphs, not for tool-calling agents.** `test_scale_calibrator.py` and (separately) the Rubric/Interrogator graphs all pass cleanly against `groq:llama-3.3-70b-versatile` - genuinely free, no code changes, just swapping `GRILLD_AI_MODEL`. But the full 10-agent roster test (which needs `market_analyst` to actually call the `tavily_search` tool) failed on Groq with `groq.BadRequestError: tool_use_failed` - the model emitted malformed function-call syntax (`<function=tavily_search(...)></function>` as literal text) instead of a real tool call. This is a known reliability gap for some Llama models specifically inside an agentic tool-calling loop, not a bug in this codebase - the same model handles `.with_structured_output()` (a single-shot JSON response, no tool loop) perfectly reliably. Worth remembering as a general lesson: "supports structured output" and "supports reliable tool-calling in a multi-step agent loop" are different capability claims about a model, and passing one doesn't guarantee the other.
- [ ] **The full 10-agent live end-to-end run was not completed this phase.** After the Groq tool-calling failure above, running it against real Claude (the only model in this session confirmed to handle both structured output and tool-calling reliably) was weighed against real API cost for a genuinely long run (10 sequential agents, 4 with live web search) and deliberately not spent - discussed directly and deferred rather than assumed. What's verified instead: every individual piece (all 10 subagents registered with non-empty, spec-derived prompts; the Orchestrator compiles and its system prompt encodes the correct delegation order; `GenerationService`'s control flow around a *mocked* full-roster response is fully tested, including the partial-failure and AI-service-exception paths). What's **not** independently proven: that a real end-to-end run actually produces all 15 expected files without hitting an unanticipated issue only a live run would surface (the kind of gap Phase 4's "null next_question" bug came from). Tracked here rather than silently assumed solved - the next time real budget is available for a long live-agent test, this is the one to run.

## A rollback bug found by its own test

Writing the "AI-service exception marks the run FAILED" test case surfaced a real bug before it ever shipped: `GenerationService.generate()` was originally `@Transactional`. Spring's default behavior rolls back the *entire* transaction when a `RuntimeException` propagates out of a `@Transactional` method - including the `run.markFailed()` write made *inside* the catch block, right before re-throwing. The failed run would have vanished from the database along with everything else, leaving no record that anything went wrong. Fixed by removing `@Transactional` entirely (each repository `.save()` commits on its own) - which is also the more correct design regardless of the bug, since the method wraps a slow external HTTP call (a full generation run, real minutes) that a database transaction should never be held open across in the first place.
